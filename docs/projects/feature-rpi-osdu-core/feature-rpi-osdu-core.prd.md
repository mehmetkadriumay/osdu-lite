## 1. Goals and Non-Goals

- **Goal 1**: Offer an opt-in, explicitly documented core wire contract, with checked-in public-contract fixtures and deterministic errors rather than silently ignored features.
- **Goal 2**: Make retained versions, ACL enforcement, legal validity, custom schemas and group memberships meaningful and restart-safe.
- **Goal 3**: Store uploaded bytes in the already-required Azurite service and issue real, scoped, expiring Blob SAS URLs.
- **Goal 4**: Use registered schema mappings in the existing OpenSearch service without cross-kind field-type collisions.
- **Goal 5**: Operate one Python writer, one Azurite instance and one single-node OpenSearch across **two machines, each with 16 GiB RAM**, using ARM64 images and bounded development limits.

### In Scope

- Storage v2 selected CRUD/list/batch/version/patch operations; Search v2 selected query/cursor/sort/projection/terms operations; Schema v1 selected register/get/list/lifecycle operations.
- Shared local-principal authorization across Storage, Search, File, Dataset and existing workflow submissions that mutate records.
- Durable registry, legal tags, entitlements and file bindings in the existing partition snapshot.
- Existing File v2 upload URL, metadata and download URL operations; Dataset v1 File.Generic registration, storage and retrieval instructions.
- Offline, non-destructive migration of referenced local files; restart recovery and private-LAN Raspberry Pi deployment instructions.
- Existing workflow/mock service endpoints MUST remain available with their current limited purpose and response envelopes; shared authorization and durability fixes MUST NOT expand their functionality.

### Out of Scope (deferred)

- DDMS integrations, new ingestion/workflow services or engines, new workflow execution modes, event delivery, Kafka or other message brokers.
- Kubernetes requirements, multiwriter coordination, replication, distributed transactions, HA/failover or production durability claims.
- OIDC/JWT/Entra integration, policy engines, nested entitlement groups, advanced legal policy, tenant provisioning or cross-partition sharing. Local bearer identities are explicitly a development mechanism.
- Wholesale upstream schemas/catalogs, Draft-07/full OSDU schema vocabulary, arbitrary remote references, unit/CRS/reference catalog expansion, formal OSDU certification.
- Search suggestions/highlighting, arbitrary analyzers/scripts, spatial query APIs (including bounding boxes), nested-array queries, live mapping mutation, zero-downtime index migration.
- Immediate invalidation of already-issued ad-hoc SAS URLs, automatic file garbage collection, unlimited datasets, encryption/key management services.
- Reformatting/restructuring the monolithic server beyond the concrete modules named below; release version or CHANGELOG.md changes.

## 2. Terminology

| Term | Definition |
|------|------------|
| `legacy` profile | Default wire adapter preserving demo-oriented response shapes and aliases, except the explicit safety changes in section 9. |
| `core` profile | Opt-in selected OSDU-like contract defined here, including explicit local limits and documented unsupported operations. Not a complete OSDU implementation. |
| Kind | Full `authority:source:entityType:major.minor.patch` schema identity. The entity type is not the partition. |
| Snapshot | One ETag-conditionally replaced JSON blob for the configured partition, authoritative for metadata, history and core control state. |
| Writer | One API process per partition. Threads serialize admission/metadata commits under the existing store lock; ETags detect, not coordinate, competing processes. |
| Data version | Immutable retained data payload plus system audit fields, with mutable record-wide ACL/legal/tags metadata applied on read. |
| Fence | Durable monotonically increasing generation preventing stale index jobs from resurrecting deleted or superseded records; not necessarily a visible record version. |
| FileSource | Partition-scoped opaque staging reference returned by an upload operation, not a local basename or arbitrary URL. |
| Published file | Final private blob bound to a metadata record; clients never receive a write SAS for this blob. |
| Local schema profile | Existing finite Draft 2020-12 data-only validation/mapping vocabulary, explicitly not an upstream OSDU schema catalog. |

## 4. Requirements

**Summary**: Implement only the finite profile below. Public-source contradictions are resolved explicitly; a wire-compatible response for an operation does not imply support for all its optional capabilities.

**Items**:
- **FR-001 — Profiles/contracts**: Default to `legacy`; opt in with `OSDU_COMPAT_PROFILE=core`. `/info` MUST expose profile, snapshot format, supported operation/feature names, local schema provenance and effective fixed limits, without secrets. Core supported routes accept the existing `/api/...` paths and corresponding existing prefix aliases; core MUST reject legacy-only request keys with 400 and unsupported recognized capabilities with 501, never ignore them.
- **FR-002 — Durable core state**: Format 2 MUST persist all format-1 fields plus custom schema entries, legal tags, entitlement groups/members, record-wide metadata overrides, file bindings, upload grants and an integer `revision`. Every successful authoritative mutation increments revision once and commits all affected maps atomically before success or index publication. Failed commits restore every affected map/revision and release scheduler reservations. Raw tokens, SAS strings and workflow/cursor state MUST NOT be persisted.
- **FR-003 — Local identity and ACL**: Authenticate distinct configured local principals, require operation roles, and enforce current record ACLs and legal validity on every route exposing or mutating record data, including versions, lists, batch, copy, File/Dataset metadata, instruction generation and existing workflow record admission. Owners can read/write; viewers can only read. Service roles alone MUST NOT bypass a record ACL.
- **FR-004 — Storage correctness**: Core PUT/list/batch/version/delete and duplicate detection MUST behave as specified below. Retained versions MUST NOT be automatically evicted in either profile. Exceeding bounded retention MUST reject the whole mutation before persistence. Visible record versions MUST remain monotonically increasing for each ID, including purge/recreation through retained fences.
- **FR-005 — Patch semantics**: Core metadata PATCH MUST preserve version/data audit fields; supported data JSON Patch MUST create a version only when data changes. Legacy record-shaped merge remains a separate adapter and retains its prior version-creating behavior. Shared authorization, validation and durability MUST apply to both.
- **FR-006 — Schema semantics**: Persist custom schemas, provide core raw GET/list envelopes and DEVELOPMENT/PUBLISHED/OBSOLETE lifecycle. Keep the existing bounded local validation vocabulary and built-in provenance, not a complete schema implementation.
- **FR-007 — Azurite files**: Uploaded bytes and published-file bindings MUST survive API/Azurite container recreation. Real read/write SAS MUST be generated using the already-installed SDK; no custom signing algorithm or public uploaded-file container is allowed.
- **FR-008 — Schema-driven indexing**: Every indexed data field MUST originate in the registered kind mapping. Unknown but schema-permitted data remains retrievable in Storage but MUST NOT dynamically become searchable. Different kinds MAY use the same path with different types without index corruption.
- **FR-009 — Search correctness**: Core query/cursor, queryAsOwner, projection/exclusion, sort and single-field terms aggregation MUST obey the defined contract and current authorization, including totals/aggregations. Recognized unsupported search features MUST return 501.
- **FR-010 — Migration and compatibility**: Load existing format-1 snapshots without losing IDs, versions, timestamps, fences, deletes or suppression. Preserve demos via legacy adapters and sample-file migration; explicitly document wire/safety differences and rollback.
- **NFR-001 — Resource bounds**: Keep exactly three runtime services; no SQLite, broker, coordination process or new runtime dependency. Preserve ARM64/amd64 binary/hash-pinned builds. Pi acceptance uses the two-machine allocation and workload below; capacity is a test target, not a current measured fact.
- **NFR-002 — Failure handling**: Storage loss, invalid snapshots, stale writers and missing schema dependencies MUST fail closed; an OpenSearch outage MUST NOT discard committed metadata. Recovery MUST rebuild without seed overwrite or stale job resurrection.
- **SEC-001 — Safe boundaries**: Never echo/log bearer tokens, connection strings or SAS query strings. Reject wrong partition, oversized/malformed JSON, path traversal and arbitrary FileSource URLs; authorize before generating credentials or exposing existence through record reads.
- **CON-001 — Scope/worktree**: Implementation MUST preserve all pre-existing worktree changes and the existing PRD, MUST NOT stage/revert/commit without instruction, and MUST NOT implement any out-of-scope service or catalog feature.

## 5. Risk Classification

**Risk**: 🔴 HIGH RISK

**Summary**: Moderate-sized implementation with high semantic/data-migration risk: changes touch admission, snapshots, access control, indexing and file publication. Bounded epics and fake/real-backend parity tests are required; this is not a claim that the resulting service is production-safe.

**Items**:
- **RISK-001**: Two separate stores (file bytes and metadata snapshot) cannot commit atomically. Publish final blob first, then binding snapshot; failure may leave an orphan, never a successful metadata record pointing to absent bytes. No automatic GC.
- **RISK-002**: Full-snapshot rewrite/copy costs scale with retained data and occur under a single writer lock. Fixed budgets are development limits, not platform parity. Do not substitute SQLite or another service to conceal a failing capacity gate.
- **RISK-003**: Per-kind shards cost more memory than the current single index. Eight active kinds is a hard ceiling, not a recommendation to populate all indices on a small demo; provision only kinds actually used.
- **RISK-004**: Legacy auth bypass/public uploads are unsafe. Preserving wire shapes cannot preserve those vulnerabilities; explicit safety differences are mandatory.
- **RISK-005**: Public development OpenAPI descriptions conflict internally (e.g. optional generated ID versus `required:id`; File paths include `/v2` despite the request URL). Fixtures record observed sources, and the explicit operation table resolves local behavior.
- **RISK-006**: Existing real OpenSearch suite has two reported pre-existing mismatches: `test_real_analyzers_lucene_operators_and_errors` near line65 expects backend rejection although schema admission already rejects StartM=`not-a-number`; `test_seed_reindex_delete_restore_and_reset` near line81 expects zero after provision although ensure_index rebuilds15. Record actual baseline, fix expectations only with the directly affected schema/rebuild epics. Do not hide failures or claim a clean baseline.
- **ASSUMPTION-001**: Both Pis have 16 GiB RAM, 64-bit OS and persistent SSD-backed storage on a trusted LAN. Exact Pi performance is unmeasured; ARM64 WSL container results are not Pi measurements.
- **ASSUMPTION-002**: Single partition/single writer is acceptable; tokens are managed locally. Public exposure requires a separate TLS/security deployment review.
- **FM-001**: Blob outage/conflict/corrupt snapshot =>503 or startup failure without cache-only success, seed overwrite or token disclosure.
- **FM-002**: Index unavailable/stale completion => durable Storage remains; readiness/search503 during recovery; fences prevent resurrection.
- **FM-003**: Invalid file/grant/finalization failure => no record/binding success; leaked orphan bytes documented and removable only offline after inventory.

## 8. Security Considerations

- **Data handling**: Snapshots and file blobs are private but unencrypted in this development deployment. Treat tokens, legal/ACL state and SAS URLs as sensitive. The public Azurite emulator account key is development-only; never use it for Azure production storage.
- **Input validation**: Constrain JSON/schema depth/bytes and file references. Never dereference user URLs or accept user-controlled account/container/blob routing. Output filenames are display metadata only.
- **Access control**: No default service-role bypass of record ACL. Use current authorization for historic versions, counts and signed URL issuance. Protect entitlements changes with admin role. Existing mocks are not production IAM.
- **Secrets**: Only environment/private identity file supplies tokens/connection string. No token echo in401, no credential values in `/info`, request/error logs or snapshots; redact SAS query strings in legacy proxy requests.
- **SAS limits**: One blob, minimal permissions and max1H; direct uploads cannot enforce byte quota before Azurite receives bytes. Finalization rejects blobs>256 MiB; operators MUST use disk quotas/monitoring. A256 MiB cap is not a security boundary on direct staging upload disk consumption.
- **Exposure**: Pi LAN firewall permits API8089 and Azurite10000 only from intended clients/Pi A; OpenSearch9200 only from Pi A to Pi B. HTTP/development credentials are restricted to trusted LAN. TLS/public internet readiness is not claimed.
